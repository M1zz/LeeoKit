# LeeoKit 운영 정책 (Operating Policy)

> **한 줄 요약:** LeeoKit은 로드맵도 스프린트도 없는 **인프라**다. 앱을 만들다가 "이거 공유되면 좋겠다" 싶을 때 *그 자리에서* 고치고, 안 쓰는 앱은 옛 버전에 내버려둔다. 이렇게 운영하면 "21번째 프로젝트"가 아니라 "여러 프로젝트의 공유 바닥"이 된다.

LeeoKit은 솔로 개발자가 ~20개 iOS/macOS 앱을 유지보수하며, 반복 복붙되던 코드를 한 곳에서 관리하기 위한 공유 Swift 패키지다. 이 문서는 그 운영 규칙이다.

---

## 0. 가장 중요한 원칙: 제품이 아니라 인프라

LeeoKit을 *그 자체로* 개발하지 않는다. 미래 대비 기능 추가 금지, 로드맵 금지.
**"지금 작업 중인 앱이 실제로 필요로 할 때만"** 손댄다. 이 규율이 무너지면
LeeoKit은 또 하나의 끝없는 프로젝트가 된다.

---

## 0-1. 예외: 계약 레이어는 세 번 규칙을 따르지 않는다

`LeeoAppSpec` / `LeeoMonetization` / `LeeoLegalConfig` / `LeeoCapabilities` /
`LeeoPreflight` / `LeeoManifest` 는 **코드 재사용**이 목적이 아니라 **판단의 일관성**이
목적이다. 여기에 세 번 규칙을 적용하면 존재 의의가 사라진다 — "세 앱이 같은 실수를
할 때까지 기다렸다가 제약을 건다"는 말이 되기 때문이다.

계약 레이어의 판단 기준은 다르다:

> **"이걸 앱마다 다시 고민하고 있는가?"**

그렇다면 넣는다. 단, 계약은 **판단과 제약만** 담는다. 구현체(페이월 레이아웃, 온보딩
플로우, 빈 상태 일러스트)는 여전히 앱의 몫이고 세 번 규칙을 따른다.

| 계약에 넣는다 | 계약에 넣지 않는다 |
|---|---|
| "페이월이 필요한가"의 판정 (`LeeoMonetization`) | 페이월이 어떻게 생겼는가 |
| "언제 막을 것인가"의 정책 (`LeeoGatePolicy`) | 잠금 애니메이션·토스트 문구 |
| "무엇을 갖춰야 하는가"의 목록 (`LeeoCapability`) | 그 항목의 구체적 구현 |
| 이벤트 **이름** 규약 (`LeeoEvent`) | 분석 SDK |

계약이 커지면 앱마다 채울 게 늘어난다. 필수 항목을 하나 추가하기 전에 항상 자문 —
**"이건 정말 모든 앱이 답해야 하는 질문인가?"** 아니면 선택 항목으로 둔다.

## 1. 무엇을 넣는가 — "세 번 규칙(Rule of Three)"

같은 코드가 **최소 3개 앱에서 필요할 때** 비로소 모듈로 뜯는다.
소비자가 1~2개뿐인 추상화는 거의 항상 틀린 모양이 된다.

| 넣어도 되는 것 | 넣으면 안 되는 것 |
|---|---|
| 앱 결합 없는 잎사귀 유틸 (색상/이미지/햅틱/날짜 확장) | 특정 앱 모델(`Memo` 등)에 묶인 코드 |
| 설정을 **주입받는** 매니저 (App Group ID를 파라미터로) | App Group ID·번들 ID를 **하드코딩**한 코드 |
| 디자인 토큰(공통 radius/spacing 스케일) | 한 앱만의 디자인 의견(특정 toast 색 등) |

### 디커플링 불변식
모듈 안에 앱 고유 식별자를 **절대 하드코딩하지 않는다.** 소비자가 주입한다.

```swift
// ❌ 재사용 불가 — 모듈이 특정 앱에 묶임
FileManager.default.containerURL(forSecurityApplicationGroupIdentifier: "group.com.Ysoup.TokenMemo")

// ✅ 소비자가 주입
public struct iCloudManager {
    let appGroupID: String
    public init(appGroupID: String) { self.appGroupID = appGroupID }
}
```

## 2. 어디서 개발하는가 — 앱 안에서 고친다 (컨텍스트 스위칭 없음)

LeeoKit을 "개발하러 따로 들어가지" 않는다. 로컬 path 의존성으로 연결해두고,
**작업 중인 앱 안에서 공유 코드가 필요해지면 그 자리에서 패키지 폴더를 수정**한다.

```
앱 작업 중 → 공유 코드 수정 필요 → 그 자리서 패키지 수정 →
앱에서 바로 테스트 → 되면 git tag 찍기 (= "릴리즈" 끝)
```

로컬 연결 (검증/개발 단계):
```swift
// Xcode > Add Package Dependency > Add Local...  또는 Package.swift:
.package(path: "../LeeoKit")
```

원격 고정 (안정화 후):
```swift
.package(url: "git@github.com:<me>/LeeoKit.git", from: "1.0.0")
```

## 3. 버전 정책 — SemVer 라이트

- **patch/minor** (기능 추가·버그 수정): 부담 없이 올린다.
- **major** (시그니처를 깨는 변경): *작정하고* 할 때만. 올리기 전에 항상 자문 —
  **"이거 바꾸면 N개 앱을 고쳐야 하나?"**
- 릴리즈 = `git tag vX.Y.Z`. **정기 배포 주기 없음.** 필요할 때만 태그.

---

## 4. 마이그레이션 정책 — 게으르게 (Lazy)

버전을 올렸다고 20개 앱을 동시에 업데이트하지 **않는다.**

- 각 앱은 자기 버전에 **핀 고정**한다.
- 어차피 그 앱을 만질 일이 생겼을 때만 최신으로 올린다.
- 안 건드리는 앱은 영원히 옛 버전이어도 OK.

→ 이것이 **폭발 반경(blast radius)** 을 막는 핵심. 공유 모듈 버그가
20개 앱을 동시에 깨는 사태를 구조적으로 차단한다.

---

## 5. 테스트 — 여기에만 더 투자한다

단일 앱 버그는 그 앱만 망가지지만, **LeeoKit 버그는 N개 앱을 동시에 깬다.**
그래서 공유 모듈, 특히 순수 로직(파싱·변환·포맷)에는 단위 테스트를 붙인다.
솔로가 평소보다 더 신경 쓸 유일한 지점.

```bash
swift build && swift test
```

---

## 6. 공개 범위 — 모듈별로 나눈다

| 범위 | 대상 | 이유 |
|---|---|---|
| **퍼블릭 가능** | 앱 비밀이 전혀 없는 잎사귀 (색상/이미지/햅틱) | 포트폴리오·신뢰도 이득, 부담 적음 |
| **프라이빗 유지** | App Group·키체인 그룹·모델에 묶인 매니저 | 앱 고유 정보 유출 방지 |

"전부 공개" 또는 "전부 프라이빗"이 아니다. 비밀 없는 건 공개해 이득 보고,
앱에 결합된 건 프라이빗으로 둔다.

---

## 7. 추출 우선순위 — 쉬운 잎사귀부터

직관과 반대로, "가치 커 보이는" iCloud 매니저는 App Group·모델 결합 때문에
*가장 나중에* 손댄다. 먼저 결합도 0의 잎사귀로 파이프라인을 끝까지 굴려보고
검증한 뒤, 무거운 것으로 넘어간다.

```
추출 순서 = (중복 빈도 높음) × (결합도 낮음)
1순위: Extensions, 디자인 토큰, 햅틱, Keychain 헬퍼   ← 결합도 0
2순위: 설정 주입형 매니저 (iCloud/CloudKit 등)        ← 디커플링 후
```
